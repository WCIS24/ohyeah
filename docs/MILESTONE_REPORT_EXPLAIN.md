# 里程碑报告通俗解读版

这次里程碑最重要的一点，不是“系统变复杂了”，而是我们终于把“哪些改动真的有效、哪些只是看起来合理但没有稳定收益”分清楚了。项目面对的是复杂金融查询：问题里常有缩写、年份口径、跨段证据和数值比较。比如一个问题表面上只有一句话，但真正作答时可能需要先知道“MS 是 Morgan Stanley”，再找到两个不同年份的财务数据，最后再算同比。这样的任务不能只靠大模型直接猜，也不能只做一次检索就结束。

从工程链路上看，系统现在可以拆成三层。第一层是检索器本身，也就是把相关证据找回来；第二层是检索增强模块，决定要不要在 query 侧做扩展；第三层是数值工具模块，也就是 calculator，决定是否把检索到的事实送进数值计算。之所以要拆开，是因为如果不拆开，我们只能看到“整体分数有没有变”，却看不出到底是哪一段真的起了作用。

可以把它想成一个很实际的金融分析工作流。用户提问之后，系统先要弄明白问题里提到的是哪家公司、哪个年份、哪个指标；然后要去文档里把对应证据找出来；最后如果问题要求“同比增长多少”“两年差了多少”“占比是多少”，才轮到数值计算。如果前面公司名认错了，或者年份没补全，后面的计算再认真也没有意义。所以这轮里程碑真正想回答的，不是“有没有做很多模块”，而是“这条链里到底哪一层最值得继续投资”。

这轮最稳的正向结果出现在检索器上。把 pre-FT dense retriever 换成 post-FT 之后，`full_r10` 从 `0.3246` 提升到 `0.3789`，`full_mrr10` 从 `0.2030` 提升到 `0.2554`，复杂子集和缩写子集也都一起提升。这说明“先把检索器做对”是当前项目最有效的一步，而不是一个边缘优化项。（证据：`TABLE_MAIN` 第3、4行；run_id=`20260228_055920_06d6bb/runs/20260228_055920_06d6bb_m01`、`20260228_055920_06d6bb/runs/20260228_055920_06d6bb_m02`）

检索模式的结论也很清楚。当前 seal 里，dense 明显强于 bm25，也强于 hybrid。也就是说，我们不需要在论文里写“各种模式都差不多”，而是可以很明确地说：在当前配置和任务下，dense 是唯一稳定的主模式，bm25 与 hybrid 更适合作为对照。（证据：`TABLE_MAIN` 第4、5、6行；run_id=`...m02`、`...m03`、`...m04`）

比较有意思的是 multistep。项目最初的设想是“多步检索应该更适合复杂金融问题”，这个想法在理论上完全合理，所以它作为 baseline 也合理。但真正跑出来后，multistep 基本没有带来可见的净收益。`m02` 和 `m05` 的 `full_r10` 一样，`full_mrr10` 只差 `0.0002`。本地日志还显示，多数样本不是被 `GATE_BLOCKED`，就是在放开 gate 后依然 `NO_GAP`，说明不是简单调阈值就能救回来。于是，这轮项目没有强行保住 multistep，而是把它诚实地定位成了 baseline。（证据：`TABLE_MAIN` 第4、7行；`TABLE_ABLATION` 第4、6行；run_id=`...m02`、`...m05`、`...m07`、`...m09`）

真正替掉 multistep 的，是 PQE。它本质上是一种更轻、更直接的 query 扩展办法。结果上，`m02 -> m18` 让 `full_r10` 从 `0.3789` 提升到 `0.3842`，`complex_r10` 从 `0.3951` 提升到 `0.4074`。提升不算巨大，但方向稳定，而且复杂子集最受益。更关键的是，`m19` 把 `prf_year` 关掉后，结果几乎回到 baseline，这说明 PQE 真正有用的部分不是“把简称展开”本身，而是把年份线索写回 query，让系统更容易找对证据。（证据：`TABLE_MAIN` 第4、20行；`TABLE_ABLATION` 第13行；run_id=`...m02`、`...m18`、`...m19`）

这件事为什么重要？因为它改变了我们对“复杂问题该怎么处理”的理解。原来的直觉是：问题复杂，所以系统也要走更长、更像推理的路线。现在的证据更像是在说：很多复杂问题并不是必须多走几步，而是要在一开始就把缺失的关键词、年份提示、简称还原补进去。只要 query 写得更接近答案证据的表达方式，dense retriever 就已经能把很多问题解决掉。这个发现对论文很有价值，因为它把主线从“复杂控制流”转成了“更有针对性的 query reformulation”。

calculator 的情况则要保守得多。它不是完全没用，而是当前只能算“诊断模块”。原因很简单：它经常带来更高 coverage，却带不来更高的 numeric EM。比如 `m11 -> m12` 时，coverage 从 `0.6180` 提高到 `0.6695`，但 EM 从 `0.3964` 降到 `0.3197`；后面放开 gate、扩大任务类型，也没有形成稳定闭环。这说明系统现在更容易“算一些东西”，但还不够容易“算对东西”。所以现在最合理的定位不是把 calculator 写成主贡献，而是把它写成一个暴露路由与 fact selection 问题的诊断接口。（证据：`TABLE_NUMERIC` 第13至17行；run_id=`...m11`、`...m12`、`...m13`、`...m15`）

组合模块 C 也不能夸大。这里的 A 是 PQE，B 是 calculator，C 是两者一起开。当前 seal 里，`m12 -> m20` 的确让 numeric coverage 从 `0.6695` 升到 `0.6867`，说明 retrieval 变好以后，更多样本进入了 numeric answer 链路；但 numeric EM 却从 `0.3197` 降到 `0.3079`。也就是说，A 和 B 确实有交互，但这个交互还没有变成“最终答案更可靠”的闭环收益。补充的本地 comboC 审计矩阵也说明，不论是 A-only 还是 C-full，都是 coverage 换 EM，没有形成稳定正收益。所以这部分现在只能写成“有交互、未闭环”，不能写成“成功解决数值链路”。（证据：`TABLE_NUMERIC` 第14、22行；run_id=`...m12`、`...m20`；补充证据：`docs/SEAL_CHECK_comboC.md`）

这也是为什么这轮报告要特别强调“不能夸大”。做实验时最容易出现一种错觉：只要系统能覆盖更多样本，就觉得它变强了。但对于金融问答，覆盖更多问题而经常算错，价值并不高。比起“能回答更多”，论文更需要的是“回答更可靠”。所以我们现在宁可把组合模块 C 明确写成未闭环，也不把它包装成半成品成果。这样的写法看起来保守，实际上更专业，因为它把下一步要补的短板说清楚了。

从复现角度看，这轮项目已经到了可冻结状态。封条入口被固定成四条命令：先跑 smoke，再跑 seal matrix，再生成 tables，最后生成 plots。正式证据不靠 `outputs/` 入仓，而是落在 `docs/TABLE_*`、`docs/SEAL_*` 和 `thesis/figures_seal/**` 上；本地 `outputs/**` 只作为审计补充。这一点对论文非常重要，因为它保证了别人即使不拿到你的本地运行目录，也能先通过文档看到正式结论，再按命令本地复现。

这套封装方式还有一个很现实的好处：它把“可以提交给导师和答辩委员会看的内容”与“本地调试现场”分开了。前者是表格、报告和图；后者是日志、配置快照和每个 run 的细节文件。这样做以后，论文写作不会被一大堆运行目录拖住，复现也不会依赖某个本地路径是否还在。对一个要进入毕业论文阶段的项目来说，这种整理工作本身就是里程碑的一部分。

如果要用一句更“答辩友好”的话总结本次里程碑，可以说：这轮工作把复杂金融查询的有效改进稳定地收敛到了 retrieval 侧，证明了 retriever FT 和 PQE replacement 是当前最可靠的主线；同时也清楚地证明了 multistep 目前只是 baseline，calculator 与组合模块 C 目前还没有形成可宣称的闭环收益。这个结论并不夸张，但足够扎实。

如果再进一步说这次工作的意义，可以概括成三点。第一，我们已经知道主增益在哪里，不必再把时间平均花在所有模块上。第二，我们已经知道哪些模块目前只能当 baseline 或诊断工具，不必为了叙事好看而硬写成创新。第三，项目已经从“实验探索状态”进入“可冻结、可写论文状态”，后续工作重点不再是大范围试错，而是沿着已经定位清楚的几个短板做精修。对毕业论文来说，这比再多几个零散实验更重要。

缺证据项清单：无。
